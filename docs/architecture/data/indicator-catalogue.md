# Indicator catalogue

**Last Updated**: 2026-06-04

The indicator catalogue is the contract that names every measure yen-gov serves, its unit, its grain reach, its facet axes, and the renderer hints that consume it. The schema lives at [`datasets/schemas/indicator-catalogue.schema.json`](../../../datasets/schemas/indicator-catalogue.schema.json); the row shape (columns, FK targets, denormalised coverage fields) is described in [docs/architecture/data/canonical-store.md section 6](canonical-store.md). The id grammar + naming policy lives in [docs/concepts/indicator-naming.md](../../concepts/indicator-naming.md). This doc is the home for the catalogue's **design rationale** and **rejected alternatives** receipts.

## How to read this doc

Three different surfaces touch the catalogue, and each has its own write path:

1. **Canonical catalogue** at `datasets/taxonomy/indicators.parquet` (compiled from `datasets/taxonomy/indicators.json`) carries the data-shape fields: id, entity_kinds, default_entity_kind, label, description, unit, cadence, value_kind, direction, denominator, comparability, family, pillar, topic_tags, methodology fields, coverage rollups. This is what the backend writer FK-validates against and what the frontend's view-model loader joins on at read time.
2. **Grapher catalogue** at `datasets/grapher/indicator_render.json` + `topic_render.json` (per ADR-0045) carries the render-shape fields: chart_type, default_mode, renderer_rules, facet_labels, dimension. Owned by the frontend; iteration cost lives in the UI layer.
3. **Legacy per-shard indicator artifact** at `datasets/indicators/in/<topic>/<id>.json` (slated for deletion in PR-D8 alongside the meadow-tier migration; see [canonical-store.md section 2b.5](canonical-store.md)) carries both data and render fields on one envelope and is the original "indicator artifact" shape per ADR-0020. Frontend reads of these shards route through the canonical allowlist in [`frontend/src/lib/canonical/indicator-from-canonical.ts`](../../../frontend/src/lib/canonical/indicator-from-canonical.ts), so the legacy schema is end-of-life - kept alive only until every consumer has migrated.

The **schema-is-the-design-system** rule (see [docs/concepts/schema-is-the-design-system.md](../../concepts/schema-is-the-design-system.md)) is preserved across the split: "schema" now means the (canonical + grapher) pair, not canonical alone. A new field that decorates "what the data IS" goes on canonical; a new field that decorates "how it RENDERS" goes on grapher.

For the per-row column list, FK contracts, and coverage rollup mechanics, read [canonical-store.md section 6](canonical-store.md). This doc fills in the WHY.

Folded into this doc per [docs/archive/plans/20260604-d-doc3-adr-retire-subplan.md](../../archive/plans/20260604-d-doc3-adr-retire-subplan.md) D-DOC3.4 (2026-06-04).

### ADR-0020: indicator-artifact-as-data-contract

Status: accepted 2026-05-11 (supersedes the per-category-component direction sketched in early Phase 5 notes). Authority: User mandate + Governance Strategist + UI/UX review.

**Context.** yen-gov began as an election viewer. The 2026-05-11 mandate expanded scope to "compare states' performance and categorise them based on categories like how are we doing on power" - socio-economic, fiscal, infrastructure, governance indicators across all states. Three architectural shapes were considered: per-category Svelte components (`PowerMap.svelte`, `HealthIndex.svelte`, `EconomyTimeline.svelte`, each with its own props, its own data loader, its own legend); a generic indicator schema + one renderer (every indicator declared as a JSON artifact validated against `indicator.schema.json`; one Svelte component renders any of them metadata-driven); a SQL-only flow (pipe everything into per-state per-topic SQLite per [ADR-0019](#adr-0019-cross-link) and let the `/explore` page do all rendering via sql.js). A side-bar concern from the Governance Strategist agent review: indicators ship with significant honesty caveats - comparability, attribution geography, methodology vintage, series breaks - and these caveats must reach the citizen reliably. A per-component world makes these caveats opt-in and easy to forget.

**Decision.** Adopt the generic-artifact-plus-renderer option. The artifact is the contract; the renderer is its implementation; the schema bumps cascade through both with clear minor/major rules per the ADR-0014-style discipline (the older `0014-sqlite-emitter.md`, now archived). Citizen consistency: every indicator reads the same way - title, comparability banner, coverage caption, time slider, map, legend, notes, license. Honesty enforcement is structural: routing every indicator through one renderer means the comparability banner, coverage caption, methodology caption, and license chip always appear when their corresponding fields are set; they are not contingent on a per-indicator component author remembering them. Velocity: the roadmap calls for 30+ indicators across 8 categories - one generic component scales, thirty per-indicator components do not. Schema-driven evolution: new honesty fields (v1.1 added 7 of them: `attribution_geography`, `comparability`, `funding_split`, `implementing_authority`, `methodology_vintage`, `series_breaks[]`, `icon`) propagate to every indicator chart in one renderer change. With per-category components each would need a port.

What goes IN the artifact: provenance (`sources[]`, `license`, `coverage`); editorial honesty (`comparability`, `attribution_geography`, `funding_split`, `implementing_authority`, `methodology_vintage`, `series_breaks[]`, `notes`); rendering hints (`value_kind`, `direction`, `scale_hint`, `unit`, `denominator`, `icon`); data (`rows[]` as long-form `{entity_id, time, value, facet}`). What STAYS OUT: per-component layout overrides (no "render this with the candle-chart variant" flag - the renderer choice is in code); sourced commentary or analysis (those belong in `notes/` or a future blog directory, not in indicator artifacts); computed quantities derived from other indicators (per-capita, growth rates - these are renderer-time computations enabled by `denominator` and series semantics, not pre-computed columns).

Schema discipline: minor bumps (`1.0` -> `1.1`) are additive (new optional fields, no data migration required); major bumps (`1.x` -> `2.0`) are breaking (require a migration of all consumer artifacts and a from/to mapping in [docs/reference/schemas.md](../../reference/schemas.md)). The validator strictly enforces `$schema_version` equality with `x-version` (per CLAUDE.md section 11); every bump appends to `x-changelog` with date and the agent/review that motivated it.

**Consequences.** Data review burden moves to the editorial layer (adding an indicator now requires answering "is this comparable across states?" and "where is this attributable?" before publication - that is a good burden, it forces the question civic-data sites usually duck). The renderer becomes a critical path (a bug in `IndicatorChoropleth.svelte` blocks every indicator; mitigated by 22 vitest cases pinning the pure helpers in `indicators.ts` and exercising the Svelte template on every state-overview page in dev). Schema versions multiply (every minor field needs a changelog entry; every consumer fixture needs `$schema_version` bumped; lived with via the strict validator and the additive-only minor-bump policy). Per-indicator overrides are deferred (if a future indicator genuinely needs a custom visual - e.g. an electoral-swing arrow chart - it will live as a sibling component, not a flag on the artifact; the indicator system is not the universal viz toolkit, it is the default surface for "value over space and time").

> **DOCTRINE NOTE (2026-06-04, plan section 22.7).** ADR-0020's artifact-as-contract rule survives the CSV cutover verbatim. The schema for the LEGACY per-shard `indicator.schema.json` v4.4 is end-of-life and will be deleted in PR-D8 alongside the meadow-tier migration; the doctrine "the artifact is the contract" stays binding for the CSV writer's `read_csv(columns=...)` boundary (per plan chunk B1). The schema-is-the-design-system rule (companion concept doc) is preserved; what changed is the storage format, not the contract.

### ADR-0026: lift-collection-inventory-out-of-indicator-artifact

Status: accepted 2026-05-17 (superseded by [ADR-0030](canonical-store.md#adr-0030-canonical-store-duckdb-wasm) on the collection-inventory-as-overlay concept - that concept is replaced by `datasets/manifest.json` plus denormalised `coverage_*` columns on the catalogue). Authority: User + Gregor (Architect) + Fowler (Engineering) + Hans (Governance).

**Context.** Indicator schema v3.0 required a `collection_inventory` block on every artifact:

```json
"collection_inventory": {
  "status": "complete | partial | empty",
  "frozen": false,
  "refetch_requested": false,
  "last_collected_at": "2026-05-16T08:31:12+00:00",
  "observed_periods": [ {key, label, frequency}, ... ],
  "pending_periods":  [ {key, label, frequency}, ... ],
  "unavailable_periods": [ {period, geographies?, reason}, ... ]
}
```

plus a sibling `series_spec.expected_geographies` / `series_spec.expected_periods` / `series_spec.expected_periods_inference` describing the promised shape. That one block was carrying three unrelated jobs: publisher promise (what RBI/CEA/MoSPI says it will publish for this series - slow-changing, hand-authored or derived from the series's own metadata); operator scoreboard (what yen-gov has actually pulled, what is still pending, what is operator-frozen, what is acknowledged-unavailable - wall-clock heavy, hand-curated overlay, NOT citizen data); citizen completeness banner (the small "we have N of M periods; last fetched X" hint shown on every indicator card).

Stuffing three jobs onto one block produced four concrete defects: re-derive smear (`inventory.last_collected_at` was computed as `max(sources[].fetched_at)` - every Fetcher re-stamp leaked into the artifact even when rows were byte-identical); Hans/nuclear-in-Goa false-pending (`pending_periods = expected_periods - observed_periods` was a cross-product blowup - if `expected_geographies = ALL_STATES` and `expected_periods = [FY24]` and Goa had no nuclear capacity, the cross-product pretended Goa-FY24 was "pending collection", a row that will never exist); operator-set fields buried in a citizen artifact (`frozen` and `refetch_requested` are operations primitives that operators want to edit in bulk across many indicators, not 110 separate files; they also have no place being content-hashed); schema bloat amplifies all four (every artifact carried a `collection_inventory` block whether or not it had any operator state at all, duplicating the default-empty case 110 times).

The 1-thing-per-field rule (lesson-2026-05-16) made the diagnosis surgical: a field that means three things means none of them.

**Decision.** Lift `collection_inventory` and `series_spec.expected_*` out of the indicator artifact entirely (schema v3.0 -> v4.0). Spread the three jobs across three surfaces, each with one job:

| Job | New surface | Schema |
| --- | --- | --- |
| Publisher promise (expected periods + geographies) | absorbed by the completeness index (follow-up) | `datasets/schemas/indicators-completeness.schema.json` |
| Operator scoreboard (frozen / refetch / unavailable / first-collected) | sparse hand-edited overlay `datasets/_ops/indicators-operator-state.json` | `datasets/schemas/indicators-operator-state.schema.json` v1.0 |
| Citizen completeness banner (status, observed count, last-collected-at) | derived index `datasets/_ops/indicators-completeness.json` | `datasets/schemas/indicators-completeness.schema.json` |

Concretely: `indicator.schema.json` v4.0 removes `collection_inventory` (required + properties); shrinks `series_spec` to `{description}` only; bumps version. A new `indicators-operator-state.json` envelope `{$schema, $schema_version: "1.0", indicators: {<id>: {frozen?, refetch_requested?, unavailable_periods?}}}` is sparse (only indicators with non-default flags appear) and hand-edited. `indicators-completeness.json` regenerates from `rows[].time` (observed_count), `sources[].fetched_at` (last_collected_at), and the operator-state overlay (frozen, unavailable_count). A one-shot migration `tools/rip_to_v4.py` walked 110 indicators, stripped the blocks, bumped the version, and seeded the operator-state overlay from any pre-existing values. Frontend `IndicatorArtifact` type loses `collection_inventory?`; `SeriesSpec` shrinks to `{description}`. `AboutThisData.svelte` drops the per-indicator Coverage block - citizens now see completeness on `/data-completeness` which already exists and reads the index.

**Consequences.** Bug-fix consequences: the Hans/nuclear-in-Goa cross-product is structurally impossible (there is no `expected_periods x expected_geographies` to take a difference against); the `last_collected_at` smear cannot leak into the citizen artifact (the field is no longer in the artifact); operator state is editable as a single small file rather than 110 file-touches. Contract consequences: schema v4.0 is a MAJOR bump per CLAUDE.md section 11 (removing a required field is breaking); all 110 artifacts were rewritten by `tools/rip_to_v4.py` in the same commit (there is no half-migrated intermediate state); any external consumer that read `collection_inventory.*` or `series_spec.expected_*` fails loud (key missing) rather than silent-default-to-empty. Operator workflow consequences: setting an indicator frozen now requires editing `indicators-operator-state.json` (one file) and re-running the completeness emitter (the previous workflow of editing one of 110 artifact files and re-running validate is gone); hand-authored `unavailable_periods` move from the artifact to the overlay (shape unchanged); `refetch_requested` is currently un-wired (no adapter reads it yet) - it exists in the overlay schema so the operator UX can land before the adapter wiring. Citizen-facing consequences: `AboutThisData` panels no longer carry the small Coverage block; the `/data-completeness` route remains the single citizen surface that answers "how complete is this dataset?", which is honest since per-indicator coverage was always an approximation anyway; the Scope sub-section no longer says "Tracked for N geographies" - if a future commit reinstates a geography count, it should source it from the observed rows, not from a publisher-promise field. Test consequences: 502/502 backend tests pass; `test_core_io.py` was updated for v4.0; `npm run check` reports 0 errors on the frontend.

> **DOCTRINE NOTE (2026-06-04, plan section 22.7).** The three-jobs-one-field diagnosis survives the CSV cutover verbatim. Under the long-format CSV regime per plan chunks B1/B2b, the catalogue moves to `datasets/data/_catalogue/indicators.csv` (or equivalent), the operator-state overlay stays a hand-edited sparse JSON file in its current location, and the completeness index is regenerated from `datasets/data/datapoints/**/*.csv` rows (observed count) + the `datasets/data/entities/source.csv` ledger (last-collected-at, derived from operator wall-clock at write time per CLAUDE.md section 10 carve-out). The three-surfaces split is the structural fix; the format is packaging.

### ADR-0045: grapher-catalogue-split

Status: accepted 2026-05-26. Authority: User (autonomous mandate, 2026-05-26 - "visualization is bleeding into storage; renderer rules belong in a frontend-owned grapher catalogue") + Gregor (contract seam) + Hans + Max (data shape - confirm what stays on canonical). Refines [ADR-0020](#adr-0020-indicator-artifact-as-data-contract): the indicator artifact remains the data contract; this ADR carves out the render-shape fields into a sibling catalogue.

**Context.** Today the canonical indicator catalogue ([datasets/schemas/indicator-catalogue.schema.json](../../../datasets/schemas/indicator-catalogue.schema.json)) and the topic catalogue ([datasets/schemas/topic-catalogue.schema.json](../../../datasets/schemas/topic-catalogue.schema.json)) carry render-shape fields: `indicator-catalogue.schema.json` ships `renderer_rules` (controlled-vocabulary array; ~30 livestock-block rows populate it); `topic-catalogue.schema.json` ships `chart_type` + `dimension` (per artifact ref); the legacy per-shard `indicator.schema.json` v4.4 ships `chart_type`, `default_mode`, `facet_labels` (slated for deletion in PR-D8 once Phase D rips the 69 legacy shards). The fan-out is three schemas, not one. These fields encode HOW the data should render, not WHAT it is - they couple the canonical data store to today's frontend chart taxonomy. Two failure modes follow: storage-layer churn on UX iterations (a designer change to "stacked area becomes default for fuel-mix on `/t/energy`" touches `topics.json` (`chart_type: "stacked-trend"` -> `chart_type: "stacked-area"`), regenerates a parquet, requires a 5-gate DoD on the BACKEND, and lands as a data-shape PR - wrong layer); render-vocabulary drift across schemas (`chart_type` on the legacy per-shard schema, `chart_type` on the topic catalogue, and the frontend's `RendererRuleSlug` union in [frontend/src/lib/indicators.ts](../../../frontend/src/lib/indicators.ts) are three separate authorities that all answer the same question and drift, no single owner is the source of truth). OWID's `Grapher` is the precedent for the separation: a `Variable` (data) carries no chart hints; a `Chart` config (render) is a sibling artifact authored by the visualisation team. yen-gov is small enough not to have separate teams, but the schema seam is the same.

**Decision.** Render-shape fields MUST live in a frontend-owned grapher catalogue at `datasets/grapher/`, not on canonical or topic catalogues. New schemas (PR-A3a, additive): [datasets/schemas/grapher-indicator-render.schema.json](../../../datasets/schemas/grapher-indicator-render.schema.json) v1.0 per indicator (`chart_type`, `default_mode`, `renderer_rules[]`, `facet_labels{}`); [datasets/schemas/grapher-topic-render.schema.json](../../../datasets/schemas/grapher-topic-render.schema.json) v1.0 per `(topic_id, indicator_id)` tuple (`chart_type`, `dimension`). Seed files: [datasets/grapher/indicator_render.json](../../../datasets/grapher/indicator_render.json) seeded from today's `indicator-catalogue.renderer_rules` + 69 legacy per-shard `chart_type` / `default_mode` / `facet_labels`; [datasets/grapher/topic_render.json](../../../datasets/grapher/topic_render.json) seeded from today's `topic-catalogue` per-ref `chart_type` + `dimension`. The grapher catalogue is read by the frontend at build time (or HMR module-graph fetch in dev); NOT read by any backend write path; validated by Tier-A. Schema changes (PR-A3c, deletions; v2.0): `indicator-catalogue.schema.json` v2.0 DELETEs `renderer_rules` (bump `x-changelog`); `topic-catalogue.schema.json` v2.0 DELETEs `chart_type` + `dimension` (bump `x-changelog`); the legacy per-shard `indicator.schema.json` v4.4 keeps those fields alive until PR-D8 deletes the schema entirely (don't double-cut - the legacy schema is on the rip queue). Reader migration (PR-A3b): every frontend read-site for the removed canonical fields routes through `frontend/src/lib/grapher/catalogue.ts` (new) instead of reading the canonical row directly. Parity tests in `catalogue.parity.test.ts` (ships with PR-A3a) assert that every indicator the old reader knew about returns identical values through the grapher catalogue.

**Consequences.** Positive: canonical data store stops shipping UI hints (designer changes to chart shape do not touch backend pipelines); one owner per question (data shape on canonical, render shape on grapher); the grapher catalogue is `tools/`-class - a frontend artifact citizens never see directly, iteration cost drops; schema-version drift between three authorities collapses to one (grapher). Negative: one extra read step in every chart path (grapher-catalogue lookup) - caught by parity tests; the lookup is O(1) against a preloaded map; 69 legacy shards still carry `chart_type` + `default_mode` + `facet_labels` until PR-D8 deletes them (documented; not double-cut); frontend allowlist learns one more import seam.

Permanent guardrails (shipped in PR-Z1): Guardrail #2 - `indicator-catalogue.schema.json` MUST NOT carry `renderer_rules` / `chart_type` / `default_mode` / `facet_labels` / `dimension` (enforced by schema v2.0 - those fields are simply absent; contract test rejects any add). Guardrail #3 - `topic-catalogue.schema.json` MUST NOT carry `chart_type` / `dimension` (same enforcement).

> **DOCTRINE NOTE (2026-06-04, plan section 22.7).** ADR-0045's grapher-catalogue split is the structural seam every CSV-era render-hint moves through. Under the long-format CSV regime, the grapher catalogue keeps its `datasets/grapher/` home and stays frontend-owned; the canonical CSV column contract under `datasets/data/_schema/columns.json` MUST NOT acquire render-hint columns. CLAUDE.md section 10 anti-pattern (add UI/render fields to `indicator-catalogue.schema.json` or `topic-catalogue.schema.json`) is binding for the CSV-era catalogue too; render hints belong in the grapher catalogue, owned by the frontend per this ADR.

## Rejected alternatives

This section preserves the rejected-alternatives receipts from the ADRs whose rationale is folded above, verbatim and append-only per [docs/archive/plans/20260604-d-doc3-adr-retire-subplan.md](../../archive/plans/20260604-d-doc3-adr-retire-subplan.md) D-DOC3.4 (2026-06-04). Each subsection is anchored as `#adr-NNNN-rejected-alternatives` for the redirect index.

### ADR-0020 rejected alternatives

- **Per-category Svelte components** (`PowerMap.svelte`, `HealthIndex.svelte`, `EconomyTimeline.svelte`, each with its own props, its own data loader, its own legend). Rejected. Makes honesty caveats opt-in and easy to forget; thirty per-indicator components do not scale; new honesty fields require a port per component instead of one renderer change.
- **SQL-only flow** (pipe everything into per-state per-topic SQLite per [ADR-0019](canonical-store.md#adr-0019-dataset-topology-and-column-discipline) and let the `/explore` page do all the rendering via sql.js). Rejected as the citizen-default surface. The `/explore` page is the right home for power-user ad-hoc queries; it is the wrong home for the citizen-default view because citizens land on a state page and expect a curated narrative not a SQL prompt, honesty caveats need to be editorial (hand-written comparability banner copy) not derived from a SQL row, and the indicator schema's `notes`, `methodology_vintage`, `comparability` fields are exactly that editorial layer. Both surfaces coexist - indicators ship as JSON artifacts for the curated view, an emitter additionally projects them into per-state SQLite for the explore surface.

### ADR-0026 rejected alternatives

- **Alternative A - keep the block, just stop re-stamping.** Was: leave the schema at v3.0, fix only the smear by content-hash gating writes (which we did anyway in commit 1d2983c) and forbid re-deriving `last_collected_at`. Rejected because it left the three-jobs-one-field defect intact; the Hans/nuclear-in-Goa false-pending bug would have stayed; operator state would still have been buried in 110 separate citizen artifacts.
- **Alternative B - split `collection_inventory` into three siblings INSIDE the artifact.** Was: add `publisher_promise`, `operator_state`, `derived_coverage` as three top-level blocks under `IndicatorArtifact`. Rejected because operator state still doesn't belong in citizen-facing data, and the operator UX is "edit many indicators at once" not "open 110 files". Splitting fields without moving surfaces would have failed both the contract clarity and the operator workflow tests.
- **Alternative C - move only `collection_inventory`, keep `expected_*` in `series_spec`.** Was: lift the derived/operational block, leave the publisher-promise fields where they were. Rejected because `expected_periods` is the input to the false-pending bug - without expected, there is no false-pending. Also: the publisher promise is NOT per-indicator authored data today (it was synthesized from observed rows during the v1.6 fold), so leaving it in the artifact would have left a field that the framework had no honest way to populate.

### ADR-0045 rejected alternatives

ADR-0045 does not enumerate formally-rejected siblings - the decision was a unidirectional split (render fields move from canonical/topic catalogues to a new grapher catalogue). The retired position is the pre-split status quo (render fields lived on `indicator-catalogue.schema.json` `renderer_rules` + `topic-catalogue.schema.json` `chart_type` + `dimension` + legacy per-shard `chart_type` + `default_mode` + `facet_labels`); the rationale for why that status quo is wrong is folded into the Design rationale above (storage-layer churn on UX iterations; render-vocabulary drift across three schemas). The permanent guardrails enforce the new direction.

### ADR-0024 rejected alternatives

Archived 2026-05-25 (superseded by PR 7b - the per-state `state_installed_capacity_by_source_mw` shard, lifted by the canonical-store pivot, carries the facetted shape natively; the backend composer and the composed `installed_capacity_by_source_mw.json` artifact were retired). Body preserved verbatim at [`docs/archive/decisions/0024-backend-aggregator-for-facetted-indicators.md`](../../archive/decisions/0024-backend-aggregator-for-facetted-indicators.md). Trace: **backend Aggregator composer for facetted indicators (per archived ADR-0024)**.

The retired position (Option B, the accepted decision at the time): a new backend composer reads N upstream artifacts and emits a single composed artifact with `facet` rows; the frontend adapter reads ONE file. Pipes-and-Filters / Aggregator pattern. The Pipes-and-Filters / Aggregator-vs-frontend-Adapter reasoning recorded in the ADR remains the doctrine for any future facetted composition need where a single upstream shard cannot satisfy the chart - the doctrine outlives the specific composer.

The siblings ADR-0024 itself rejected at decision time were:

- **Option A - frontend multi-file adapter** (`StackedTrend` adapter fetches N artifacts in parallel, joins them by `entity_id` + `time`, synthesises a facetted view-model in-browser; no backend change). Rejected because it pushes Aggregator concerns into a Translator (Holy Law #5 - structural fixes only); repeats the join on every page load (waste); sets a bad precedent for the next composed indicator; provenance merging would happen at render time, untested and on the hot path. The only argument for Option A was "ships faster" - that argument loses to Holy Law #5.
- **Option C - augment each per-fuel file with a `facet` field, leave them separate**. Rejected because the chart still needs to fetch N files; nothing structural changes; complexity is added (every artifact has an unused `facet` field) without removing the join.

What superseded ADR-0024 itself (the WHY of the archive move): PR 7b (2026-05-25) shipped the `state_installed_capacity_by_source_mw` shard from the canonical-store pivot. The per-state shard carries the facetted shape natively (one row per `(state, year, fuel)` triple), so the backend composer that previously aggregated 8 per-fuel artifacts became unnecessary - the canonical writer already does the equivalent join at write time per [ADR-0030](canonical-store.md#adr-0030-canonical-store-duckdb-wasm) section 11.4 (aggressive materialisation). The composer was retired and the composed artifact deleted in PR 7b. The Aggregator pattern doctrine survives the supersession for future cases where a canonical-store row is not yet the answer.
