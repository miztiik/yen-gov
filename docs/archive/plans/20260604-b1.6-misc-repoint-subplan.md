## Why this exists

Parent sub-row B1.6 reads as one row but expands across seven distinct caller files spanning four subsystems (`sources/`, `pipeline/`, `cli.py`, `canonical/adapters/`) with twelve total `write_artifact` call sites. The shapes are heterogeneous: `cli.py` alone holds six sites inside an election-import command that loops over candidate rows + reconciliation summaries; `pipeline/people_ingest.py` and `pipeline/reference.py` emit canonical reference rows rather than per-source ingest output; `canonical/adapters/eci_ae_panel.py` is an election-domain adapter. Per CLAUDE.md correction-level discipline (4+ files structural -> propose breakdown first) and grandparent plan section 24.5, the right shape is a thin parent row + this sub-plan, mirroring the B1.4 precedent (archived at [docs/archive/plans/20260604-b1.4-iced-repoint-subplan.md](20260604-b1.4-iced-repoint-subplan.md)) and the B1.5 precedent (archived at [docs/archive/plans/20260604-b1.5-rbi-repoint-subplan.md](20260604-b1.5-rbi-repoint-subplan.md)).

## Scope

In scope: every `write_artifact(...)` call site under `backend/yen_gov/sources/cea_*`, `backend/yen_gov/sources/datagovin_ogd`, `backend/yen_gov/sources/india_geodata`, `backend/yen_gov/pipeline/*`, `backend/yen_gov/cli.py`, and `backend/yen_gov/canonical/adapters/eci_ae_panel.py`, re-pointed onto `yen_gov.canonical.csv_writer.write_csv` per the file-class contract in `datasets/data/_schema/columns.json`. Per grandparent plan section 23.1 the OLD `core/io.write_artifact` survives until B3; this sub-plan does NOT delete it. Each family records its alongside-vs-instead-of choice in the family PR body.

Out of scope: iced_* (B1.4, done); rbi_* (B1.5, done); deletion of `core/io.write_artifact` or any parquet artefact (B3); fetch-code delete (B4); `entities/source.csv` builder (B2a); concept-catalogue authoring (B2a).

## Pre-flight - source-id + concept-id readiness

Each ingest must derive `source_id` via `yen_gov.canonical.citation.derive_source_id(producer, title, vintage)` (CLAUDE.md Holy Law #9, section 12; ADR-0042 vintage semantics). The validator gate (grandparent B1.3) enforces `source_id` FK presence in `datasets/data/entities/source.csv`; that file is built by B2a. While B2a is upstream, the writer (grandparent B1.2) does NOT itself check the FK; the validator does. Each family PR runs the writer and an isolated writer-unit assertion; the FK-presence assertion is exercised once `entities/source.csv` lands (B2a) via the existing `fk-validator` gate run on the suite. No mock `entities/source.csv` is created in this sub-plan (CLAUDE.md Holy Law #7). If a family's concept_id does not yet exist in `datasets/data/concepts.csv` (also B2a), the family PR records the gap in its PR body + leaves a DEFER-to-B2a marker; no row is emitted with a silently null concept_id.

### B1.6.1..7 per-family pattern (binding, mirrors B1.5.1..5)

Each family PR:

1. Imports `write_csv` from `yen_gov.canonical.csv_writer` and `derive_source_id` from `yen_gov.canonical.citation`.
2. After (alongside) the existing `write_artifact(...)` call, builds the long-format CSV row list per the indicator's file class (`datasets/data/datapoints/geo/*.csv` for state-grain; same glob for national-grain rows with `entity_id="IN"` per grandparent plan F4 freeze; `datasets/elections/assembly/state=*/election=*/candidacies.csv` for election candidacy rows in B1.6.6 / B1.6.7).
3. Calls `write_csv(path=<target>, file_class=<class>, rows=csv_rows)`.
4. `variable_id` honours grandparent plan section 21.6 / 21.12: no `__`; kebab-case `<measure>-<unit>-<facet>` per ADR-0044; never grain-prefixed.
5. Records in PR body: (a) alongside-vs-instead-of choice + reason; (b) per-indicator (file_class, variable_id, entity_id source, source_id triple) table; (c) concept_id binding (or DEFER-to-B2a marker if missing).
6. Existing meadow-JSON output stays in place (alongside) for this sub-plan; instead-of is deferred to B3 per grandparent plan section 23.1.
7. Faceted indicators split into per-facet variable_ids until the writer supports facet columns (csv_writer.py top-of-file note).
8. `source_id` derivation: producer / title / vintage per family - cea_installed_capacity = "Central Electricity Authority" / "Executive Summary on Power Sector" / monthly edition; datagovin_ogd = per-resource publisher / resource title / resource vintage (DEFER if metadata absent); india_geodata = upstream cartographer / dataset title / release year; pipeline/* canonical reference emissions = producer "yen-gov canonical pipeline" / title per reference table / vintage per build (DEFER concept_id where not yet in concepts.csv); cli.py + canonical/adapters/eci_ae_panel.py = "Election Commission of India" / per-election Statistical Report title / election-year vintage.
9. Gate: `writer-unit` (the row-builder helper is unit-tested with a tmp_path fixture under `backend/tests/test_<family>_csv_repoint.py`) + `suite-green` (full pytest at merge).

### B1.6.6 (cli.py) addendum - alongside: NEITHER, rationale recorded

Evaluated under sub-plan section §B1.6.1..7 point 5. The six in-scope `write_artifact(...)` call sites at `cli.py:1447,1464,1522,1685,1698,1780` are evenly split across two sibling command paths (the `/api/`-ingest path `eci_statreport` and the hand-import path `eci_statreport_emit`), each emitting the same three artifact shapes per election + state: (i) per-AC `ConstituencyResult` JSON written in a loop to `datasets/elections/<event>/<state>/results/<eci_no>.json`; (ii) a per-state `ResultSummary` JSON at `result.summary.json`; (iii) a per-state `PartiesSnapshot` JSON at `parties.json`. All three are operator-curated election artifacts that target the legacy `datasets/elections/<event>/<state>/` JSON tree (CLAUDE.md `MIGRATING` per grandparent plan chunks B2b/X1b), NOT the post-rip canonical CSV tree under `datasets/elections/{assembly,parliament}/`.

The closest matching CSV file classes in `datasets/data/_schema/columns.json` are `datasets/elections/assembly/state=*/election=*/candidacies.csv` (one row per constituency x candidate) + `datasets/elections/assembly/state=*/election=*/summary.csv` (one row per constituency, derived from candidacies) + `datasets/data/entities/party.csv` (canonical aggregated party reference). None of the three fits a direct re-point at this write seam:

1. **`ConstituencyResult` -> candidacies.csv shape mismatch.** `ConstituencyResult.candidates` is a TRUNCATED `top_n` view (with `OthersBucket` collapsing tail candidates into a single name-less bucket and `NotaResult` carried separately), driven by `cfg.results.top_n_candidates` + `collapse_others`. The candidacies.csv file class requires one row per candidate with mandatory `candidate_name`, `position`, `result` (`won`/`lost`/`forfeit`). Mapping the truncated view would either drop tail-candidate rows (data loss) or synthesize a fake "Others" row with no `candidate_name` (contract violation). The full untruncated candidate list lives upstream in the Section-10 parser output `raw.sections[].candidates` (`CandidateRow` per `sources/eci/statistical_report_detailed.py`), NOT in the artifact emitted at this seam. Emitting candidacies.csv here would require re-deriving full candidate rows from `raw` (with `entity_id` + `party_id` + `source_id` derivation), which is new data emission grafted onto an unrelated write seam, not the "alongside the existing write_artifact" re-point pattern that B1.6.1..3 follow.
2. **`ResultSummary` -> summary.csv shape mismatch.** `ResultSummary` is per-state-aggregated (`party_totals` + `alliance_distribution` + state-wide `totals`), whereas the summary.csv file class is per-constituency (PK `entity_id`, columns `winner_candidate` / `runnerup_candidate` / `margin_votes`). They are not the same shape; summary.csv is the derived per-AC projection that B2a will aggregate from candidacies.csv per the file's own `notes` ("Derived projection of candidacies.csv (parity-oracle-CSV gate asserts summary == recompute(candidacies))").
3. **`PartiesSnapshot` -> entities/party.csv shape mismatch.** `PartiesSnapshot` is per-election (election + parties list with `eci_code` + `short_name` + `full_name`), whereas `entities/party.csv` is the SINGLE aggregated canonical party reference across all elections + cohorts. The per-election snapshot is one of N inputs to the canonical aggregator, not a 1:1 re-point target.

All three shapes are downstream-aggregator concerns owned by B2a (grandparent plan section 22.5: "entities/*.csv builders" and per-election `candidacies.csv` + `summary.csv` aggregators), not B1 (per-source `write_artifact` re-point). Per sub-plan §B1.6.1..7 point 6 the existing `write_artifact` calls stay in place (alongside); deletion deferred to B3. Per sub-plan §Pre-flight, no `entities/source.csv` mock is created (Holy Law #7). No CSV rows are emitted in this PR, so no `source_id` is derived and no `concept_id` bound. Gate: `docs-review` (no CSV emission added; the `writer-unit` + `suite-green` gates listed in the ledger row are replaced with `docs-review` per the alongside-NEITHER choice, recorded here for audit). Mirrors B1.6.4 #664 and B1.6.5 #666 precedents.

## Contract invariants (inherited from grandparent 22.4 + parent §Contract invariants)

1. Provenance FK mandatory: every CSV row carries `source_id` (Holy Law #9).
2. One-indicator-per-concept: each `variable_id` binds to one `concept_id` (FK to `concepts.csv`; gap allowed during B2a window with DEFER marker, never silently null).
3. Schema-per-file typed: rows handed to `write_csv` declare the file class explicitly; no `read_csv_auto` round-trip.
4. Static-first deterministic read: rows sorted upstream by (entity_id, time); no `datetime.now` in content columns.
5. ASCII-only + relative POSIX paths in any persisted artifact.
6. LGD/ECI key separation preserved (writer never invents a shared parent); election rows key on ECI codes per existing parser output.
